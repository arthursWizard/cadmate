# One active project, a fixed layout, one history folder

The user collaborates on a design by looking at it, in KiCad, FreeCAD and Finder, between your steps. That only works if
there is one current version to look at. Side-by-side versions (`main-v2/`, `main-routed.kicad_pcb`,
`main-hand3.kicad_pcb`, `enclosure-variant-b/`) make the user work out what's new, and every later step has to pick the right
copy. Over a long design this piles up hundreds of superseded files, and the user can no longer tell what's current.

So:

1. **One active project.** Every change is applied to the active project, in place. No copies to "keep the old one".
2. **History is snapshots.** When the current state is worth going back to, `project_snapshot` copies it into
   `history/<YYYYMMDD-HHMM>_<label>/` first, then you change the active files. `project_restore` brings one back.
3. **A fixed layout**, so every file has one place and one depth.

These rules are about your own habits as much as cadmate's tools: hand-made copies, generator scripts that write
`-v2` folders and instructions to another session ("build it as a new folder next to the current one") cause the same
sprawl. Apply them to everything you write and everything you ask another session to write.

## Layout

One rule shapes it: **no folder holds just one thing.** A folder is there to tell several things apart, so:

- **Tools.** One kind of design (KiCad, FreeCAD, or cadmate's protoboards): its files sit at the project root.
  Several: a folder each, `kicad/`, `freecad/`, `protoboard/`. `cadmate-project.json` records them as `"tools"`.
- **Boards, parts and protoboards.** One sits directly in its tool's place (the root, or `kicad/`, `freecad/`,
  `protoboard/`). Two or more get a folder each, named for what it is.
- **Parts are named for what's being made**: `enclosure/`, `bracket/`, `knob/`, `lid/`, from the conversation or the
  brief. Never a generic `case/` when it's a bracket. When you can't tell what the part is, ask.

A board and an enclosure, the most common shape:

```
<project>/
  cadmate-project.json     marker: name, layout version, tools
  README.md                what it is, boards, parts, what to order where, open items, decisions
  CLAUDE.md                these rules in short, for every session working in the folder
  kicad/
    main.kicad_pro  main.kicad_sch  main.kicad_pcb  main.kicad_dru
    fp-lib-table  sym-lib-table            paths as ${KIPRJMOD}/lib/...
    lib/                   project libraries: <project>.pretty/  <project>.kicad_sym  <project>.3dshapes/
  freecad/
    enclosure.FCStd        FreeCAD source
    top.step  base.step    one STEP per printed piece
    assembly.step          every piece and board placed and named (check_enclosure)
    enclosure.json         openings meant to be there, joint limits, heights from the brief
    enclosure-check.json   check_enclosure's last report
    renders/  pcb-models/  pcb-models: <board>.step exported from KiCad, for the fit
  fab/main/                generated by export_fab: Gerbers zip, BOM, CPL, assembly PDF. Regenerate, never edit
  tools/                   generator scripts and their inputs: the design's source code
  docs/                    the user's documents: datasheets, drawings, photos and notes. Never design outputs
    brief.md               every requirement the user stated, as a checklist
  history/
    HISTORY.md             index: one row per snapshot, oldest first
    20261031-1213_before-rework/   same relative paths as the project
  releases/
    RELEASES.md            index: one row per released revision
    main/A/                frozen at release: fab files as sent, renders, RELEASE.md, release.json. Never edit
  .cadmate/work/           scratch: comparisons, temp outputs. Delete when the step is done
```

Two boards and two parts: each gets its folder, and what's inside is the same as above.

```
  kicad/
    main/      main.kicad_pro ... fp-lib-table, paths as ${KIPRJMOD}/../lib/...
    sensor/    sensor.kicad_pro ...
    lib/
  freecad/
    enclosure/ enclosure.FCStd  top.step  base.step  assembly.step  enclosure.json  renders/
    knob/      knob.FCStd  knob.step
```

A protoboard is a design like a board: `blinker.json` with `blinker.png`, `blinker.svg` and `blinker-build.md` from
`render_protoboard` beside it, in `protoboard/` next to the others, or at the root when it's all the project has.

KiCad only, one board: `main.kicad_pro`, `main.kicad_pcb`, ..., `lib/` and `fab/main/` sit at the project root.
FreeCAD only, one part: `bracket.FCStd`, `bracket.step`, `renders/` sit at the project root, no `fab/`. With two or
more, the same folders as above, at the root.

A board folder is named after its KiCad project (`main/main.kicad_pro`). A part folder is named for the part; the
files in it can be named as FreeCAD needs. Board and part names can't be a shared folder's (`docs`, `tools`, `lib`,
`fab`, `kicad`, `freecad`, ...).

Pass `tools` to `project_init` for what the design uses, and `boards` and `parts` if you know them; ask the user when
it isn't clear. Without `tools`, `project_init` goes by the files already there, else makes both. A marker with no
`tools` (layout 1, made before this) is `kicad/` and `case/`: cadmate keeps reading `case/` as the FreeCAD folder there.

### Going from one to two

Never move the files by hand. Each of these takes a snapshot first, then moves the files and fixes what the move
would break:

- **A second tool**: `project_add_tool kicad|freecad`. The existing tool's files move from the root into `kicad/` or
  `freecad/`; a board moves with `lib/`, so `${KIPRJMOD}` paths still resolve.
- **A second board**: `project_add_board` with the new board's name. The board at the top moves into a folder named
  after it, and its `${KIPRJMOD}/lib/...` paths (lib tables, 3D model links) become `${KIPRJMOD}/../lib/...`. File
  times are kept, so fab/ doesn't read as stale for a path change.
- **A second protoboard**: `project_add_protoboard`, the same way (its name taken from its only design JSON).
- **A second part**: `project_add_part` with the new part's name, and `current`, what the existing one is (taken from
  its only `.FCStd` when you leave it out). Its files move together, so links between them still hold.

Ask the user to save and close the files in KiCad and FreeCAD first, and to reopen them from the new place after. Then
update the layout lines in CLAUDE.md and README.md. `project_check` flags each of these states (the other tool's files
at the root, a loose board or part beside folders) and names the tool to run. Going back (two boards to one) isn't
automated: ask the user, snapshot, and move the files up yourself, fixing the `${KIPRJMOD}` paths.

`project_init` makes it (safe on an existing folder: it only adds). `project_check` lists everything out of place,
each with a fix. Run it before you tell the user a step is done.

Names: lowercase, dashes, no version or state words (`v2`, `final`, `new`, `routed`, `fixed`). A board's or part's
name is what it is (`main`, `sensor`, `power`; `enclosure`, `bracket`), not when it was made.

## Where the board gets made

cadmate assumes no board house. When a KiCad project starts, ask the user once, with the question `project_init` or
`project_fab` gives: which house, whether it assembles, which distributor, how many layers. Any answer can be "not
decided yet". Record it with `project_fab`: it goes into `cadmate-project.json` and the brief's Fab section, and
`review_pcb_layout`, `autoroute_rest` and `export_fab` read it from there. Don't ask again; when the user changes their
mind, call `project_fab` with the new value. With no house chosen, reviews skip the fab-specific limits and say so,
and `export_fab` writes the generic BOM and placement files, which any assembler takes.

## The brief

`docs/brief.md` holds every requirement the user has stated, in their words, with who said it and when: shapes,
sizes, parts already chosen, angles, looks, things they don't want. Over a design that runs for days, a shape asked for
on day one or a part the user already picked is easy to lose in the conversation; if it isn't written where every later
stage looks, a stage builds something else or asks again.

- Add to it the moment the user states a requirement or makes a choice (decision cards included), not at the end.
- Re-read it at the start of each stage (schematic, PCB, fab, mechanical parts) and before showing the user a result.
- Tick an item only once you have checked the design against it (render, DRC, measurement).
- `project_check` returns the open items under `brief`. When you report a stage done, say which items are met, which
  aren't yet and why.
- A value you assume (an angle, a height) goes in as an assumption to confirm, and you ask the user, rather than
  picking it silently.

## Enclosures

When a FreeCAD part is an enclosure (anything that closes around boards), run `check_enclosure` on its folder before
showing it to the user. The folder needs assembly.step with every piece placed and named (the printed pieces, boards
with their components, cables) and a `<piece>.step` for each printed piece. It reports pieces that collide, openings in
each shell, joints between pieces with a gap or a step, and heights. These are the defects a user otherwise finds by
eye or after printing: one piece standing above the one beside it, a gap along a seam, a slot left open in a wall, a
board pressed into a wall. A part with no assembly.step (a bracket, a knob) isn't checked.

- The first run lists every opening. Put the ones that are meant to be there in enclosure.json beside the assembly
  (name, and a box, the piece beside it, or the face), with the heights from the brief. Anything left is a hole to close.
- A step or gap that's designed (a rim, a shadow line) gets its own limit under joints, with the reason in the brief.
- `project_check` flags the assembly when the report is missing, older than the STEPs, or has errors.

## When to snapshot

Snapshot what you're about to change (`paths: ["kicad/main"]`, `["freecad/enclosure"]`, or a lone board's files),
or the whole project, when:

- the user has seen or approved the current state ("seems good", "PR good", a picked option), and the next change
  replaces it;
- the change is big or hard to undo by hand (re-placement, a new connector, reshaping a part);
- the user asks to keep it.

When something is ordered, don't snapshot: release it (below).

Not before every small step. The routing tools (`route_critical_nets`, `autoroute_rest`, `finish_routing`) snapshot the
board themselves before changing it in place, and the footprint, symbol and part writers put a replaced file into
history/ instead of a `.bak`.

The label says what the state is or what comes next: `approved-layout`, `before-rework`, `ordered`.
The note (one sentence) goes into HISTORY.md: "User approved the placement; next, routing".

## Releasing a board revision

A snapshot lets you go back; a release is the record of what was ordered. When the user orders a board, or calls a
revision final:

1. `export_fab`, then `check_ready_to_order`. Go through what it flags with the user first.
2. `project_release` with notes in the user's words (what this revision is for, what it fixes). It takes the next
   letter (A, B, ...) unless you pass `revision`. It snapshots the whole project (`release-<board>-<rev>`), copies the
   fab files, any `renders` you name and top and bottom board pictures (when kicad-cli is there) into
   `releases/<board>/<rev>/`, and writes RELEASE.md with what changed since the previous revision.
3. Tell the user the revision and the changes. If the board's title block shows another revision, the result warns:
   set it in Board Setup, re-export, release again.

A release is frozen: never edit it. A change after ordering is the next revision. `project_check` flags a release
whose files changed, or whose snapshot is gone. To open revision A again, `project_restore` its snapshot.

## Pruning history

Routing tools snapshot the board before each pass, so history grows by a board's size every time. `project_prune`
deletes the automatic snapshots (the ones tools take before changing something) beyond the newest ten (`keep`).
Snapshots taken with `project_snapshot` and released ones are never pruned. Called without `delete`, it only lists what
would go: show the user the list and the space it frees, and on their yes call it again with `delete` set to those
names, since deleted snapshots can't be restored. `project_check` suggests it once there are more than ten.

## Alternatives

When the user needs to choose between options, build them in `.cadmate/work/<option>/` (renders, a STEP, a board
copy), show them, apply the chosen one to the active project, and delete the work folder. Don't leave options in
the project, and don't make the user pick between folders. If an unpicked option might come back, snapshot it with a
label like `option-b`.

## Why it fits KiCad and FreeCAD, and where it doesn't

- **KiCad finds libraries relative to the project** (`${KIPRJMOD}/lib/...`, or `${KIPRJMOD}/../lib/...` from a board folder). A snapshot keeps the same relative
  paths and `project_snapshot` brings along the libraries a board folder references, so an old version opens in KiCad
  from history/ with its footprints and 3D models. Boards and schematics also embed their footprints and symbols, so
  they open even without the libraries. Absolute library or model paths break this: `project_check` flags them.
- **Never rename a KiCad project.** The schematic stores each symbol's reference under the project name; a copied or
  renamed project can come up with R?, U? references until it is re-annotated (KiCad's own Save As handles this; a
  file rename doesn't). Working in place means you never need to: the board is called
  `main` from the start. `project_check` flags a schematic whose annotations belong to another project name.
- **One board per folder.** KiCad pairs `.kicad_pcb`, `.kicad_sch` and `.kicad_pro` by name. A second board in the
  folder (`main-routed.kicad_pcb`) has no schematic to update from and no own rules unless its own `.kicad_pro` is
  copied beside it, which is how stray `-routed.kicad_pro` files appear.
- **Don't snapshot while KiCad has the file open and unsaved**: the snapshot is what's on disk. Ask the user to save,
  or use `kicad_pcb_save`, first. After `project_restore` the user has to reload the file in KiCad.
- **FreeCAD**: STEP files are self-contained. An `.FCStd` that links other documents (App::Link, assembly parts) stores
  relative paths when they're in the same tree; keep a part's linked documents in its own folder (or wherever the part
  sits) so snapshots and the moves `project_add_tool` and `project_add_part` make keep working. A link from one part
  to another part's file breaks when either moves: re-link it in FreeCAD after.
- **fab/ is generated.** Re-export after every board change (`project_check` flags fab files older than the board).
  Snapshots include fab/ only when you snapshot the whole project; a release keeps the fab files as ordered.
- **Git.** If the project is a git repository, commits do the same job better for text files (all KiCad files are
  text) and snapshots are still handy for the user to open an old version from Finder. Use both; don't commit
  `.cadmate/`.

## Cleaning up a project that sprawled

1. `project_init` on the folder, then `project_check`.
2. Ask the user which version of each board and part is current, if it isn't obvious from the thread. Don't guess from
   modification times alone.
3. Snapshot the whole folder as it is (`label: "before-cleanup"`), so nothing is lost.
4. Move the current files to their layout paths. Where the current board is a copy with a version name, copy its
   contents over the board named after the folder rather than renaming the KiCad project. A copied schematic keeps the
   old project name in its annotations: copy it the same way, then have the user open it in KiCad and check the
   references (`project_check` flags the mismatch). Delete the other versions
   (they're in the snapshot). Keep `tools/`: generator scripts are source, not intermediates.
5. `project_check` again until it's clean, run DRC on each board, re-export fab/.

Moving a project's own history to the Trash deletes the snapshots; say so before doing it.
